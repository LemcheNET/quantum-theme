# Quantum Plymouth boot theme

A boot splash to go with the desktop themes: a full-screen background that fades in,
and an activity spinner at the bottom centre. Optionally the same art behind the GRUB
menu.

**This part is optional, and it is different from the rest of this repository.** The
desktop themes in `bin/` run as you and write only under `~/.local` and `~/.config`.
This runs **as root**: it writes `/usr/share/plymouth/themes/`, edits
`/etc/default/grub` and `/etc/plymouth/plymouthd.conf`, and rebuilds the initramfs for
every installed kernel. Nothing else in the repository depends on it. See
[`SECURITY.md`](../SECURITY.md).

## Requirements

- **Debian/Ubuntu family**: `initramfs-tools` and GRUB. Hosts that build their initrd
  with dracut or mkinitcpio are not supported; the scripts check and refuse.
- `plymouth` plus the package that ships its `script` plugin (`plymouth-themes` on
  Ubuntu).
- `splash` on the kernel command line, and no `nomodeset`. The installer warns about
  both, and `--quiet-boot` adds `splash` if it is missing.
- Your GPU's KMS driver in the initrd, so the splash gets the native resolution rather
  than a low-resolution fallback. `prepare-boot-graphics.sh` checks, and adds it if
  needed. It works out which driver to check from the connected display: `amdgpu`,
  `i915`, `nouveau` and so on.

## What you get

| Stage | What shows | Controlled by |
| :--- | :--- | :--- |
| Firmware | Vendor logo | your BIOS, not Linux |
| GRUB menu | Optional background image | `--grub-bg`, `GRUB_GFXMODE` |
| Kernel → Plymouth | Background fading in, spinner below the glow | `theme/`, `plymouthd.conf` |
| Esc during boot | The kernel and systemd log | plymouthd itself |

The background is scaled to cover the screen. On screens wider than 2:1 the 21:9 art is
used, otherwise the 16:9 art.

## Run order

```bash
sudo bash plymouth/prepare-boot-graphics.sh                 # 1. read-only: is the KMS driver in every initrd?
sudo bash plymouth/prepare-boot-graphics.sh --apply --dry-run   # only if 1 reported FAIL
sudo bash plymouth/install.sh --dry-run                     # 2. read the plan: every file and key it will change
sudo bash plymouth/install.sh                               # 3. apply
# 4. switch to a text console (Ctrl+Alt+F3), log in, then:
sudo bash plymouth/verify.sh --preview                      #    renders 15 s; press Esc to check the log view
sudo bash plymouth/verify.sh                                # 5. read-only checks, then reboot
```

`sudo bash <script>` rather than `sudo ./<script>` works from a checkout on a `noexec`
mount.

Options worth knowing:

| option | effect |
|---|---|
| `--grub-bg PATH` | use a PNG or JPEG as the GRUB menu background; `--grub-bg plymouth/theme/background-wide.png` matches the splash |
| `--quiet-boot` | adds `quiet loglevel=3 vt.global_cursor_default=0` to `GRUB_CMDLINE_LINUX_DEFAULT`, and records the original for rollback. Esc during boot and `journalctl -b` still show everything |
| `--backgrounds DIR` | take the two backgrounds from `DIR` instead of `theme/` — see below |
| `--resolution WxH` | force the GRUB mode instead of reading the connected monitor |
| `--theme-name NAME` | install under another name (default `quantum`) |

## Backgrounds

The two files in `theme/` are **original artwork**, generated by
`build/generate_backgrounds.py`: the Quantum Dark window colour lifted slightly at the
centre and falling to near-black at the edges, so the firmware hand-off and Plymouth's
own black background meet it without a seam, plus a soft glow behind the spinner in the
spinner's own colour. They are computed in floating point and dithered once before the
8-bit conversion, which is what keeps a slow dark gradient from banding on a large
panel. The dither noise is also why the two PNGs are ~4 MiB together; a gradient that
compresses well is a gradient that bands.

```bash
python3 plymouth/build/generate_backgrounds.py --out-dir plymouth/theme   # needs numpy and Pillow
python3 plymouth/build/generate_wheel.py plymouth/theme/wheel.png          # the spinner, Pillow
```

Both are deterministic: the same seed gives the same bytes. The static gates regenerate
the backgrounds and fail if the committed PNGs have drifted from the generator.

**To use your own art**, convert it once and point the installer at the result. This
keeps images whose licence you cannot pass on out of the repository entirely:

```bash
python3 plymouth/build/prepare_backgrounds.py WIDE.png SIXTEEN_NINE.jpg --out-dir ~/my-boot-art
sudo bash plymouth/install.sh --backgrounds ~/my-boot-art --grub-bg ~/my-boot-art/background-wide.png
```

Plymouth's script module loads PNG only, so `prepare_backgrounds.py` converts JPEGs
(and drops EXIF) at that step rather than on the target at boot.

## Rollback

```bash
sudo bash plymouth/uninstall.sh --dry-run    # the plan
sudo bash plymouth/uninstall.sh
```

It restores `plymouthd.conf` `Theme=`, the `default.plymouth` alternative and its mode,
and the GRUB keys the installer set — to their values before the **first** install,
recorded in `/var/lib/quantum-plymouth/original.env` (mode 0600, directory 0700). Other
GRUB edits made since are left alone. Every run, install and uninstall alike, first
copies `/etc/default/grub` and `plymouthd.conf` to
`/var/lib/quantum-plymouth/backups/<timestamp>/`.

**`uninstall.sh` has never run for real** — only `--dry-run`. Read its plan before
trusting it, and keep the snapshot directory until you have rebooted once afterwards.

`prepare-boot-graphics.sh --revert` undoes only what its `--apply` added.

### Two guards against restoring the wrong thing

The installer refuses to proceed, before changing anything and in `--dry-run` too, if:

- `plymouthd.conf` already selects this theme but no `original.env` exists. Recording
  the "original" state then would record this theme as the thing to restore, so a later
  uninstall would put back the theme it deletes. The desktop themes' uninstaller had
  exactly that defect, found on a live host.
- `/var/lib/sovereign-plymouth/original.env` exists: this theme is already installed
  under its pre-publication name. Roll that install back with the uninstall script it
  came with first.

## How theme selection works

Two mechanisms exist, and they can disagree:

- `/etc/plymouth/plymouthd.conf` `[Daemon] Theme=`
- the `default.plymouth` alternative

`Theme=` wins when it is set. The installer sets both, then checks that the theme's
files are inside every `/boot/initrd.img-*`, since the splash is drawn from the initrd.

## Native resolution

- **GRUB:** `GRUB_GFXMODE="<WxH>,auto"`, where `<WxH>` is the connected monitor's
  preferred DRM mode. GRUB can only use modes the GPU's UEFI GOP offers; if yours is not
  among them GRUB falls back to `auto`. Check with `videoinfo` at the GRUB prompt.
- **Kernel hand-off:** `GRUB_GFXPAYLOAD_LINUX="keep"` avoids a mode switch.
- **Plymouth:** the resolution comes from your KMS driver, which must be in the initrd
  with whatever firmware it needs. For `amdgpu` that check is generic: it confirms the
  initrd carries amdgpu firmware at all, not the specific blobs your GPU generation
  needs.

## Tuning

At the top of `theme/quantum.script`: `SPINNER_Y`, `SPINNER_SIZE`, `SPIN_SPEED` (negate
it if the spinner's tail leads), and the fade speeds. Re-run the installer after editing.
If you move `SPINNER_Y`, change it in `build/generate_backgrounds.py` too and regenerate,
so the glow stays under the spinner.

## Known limits

- **Untested in this form.** It was deployed and verified — preview, two reboots, three
  displays — as `sovereign-boot` on the author's workstation, an AMD RX 7900 XTX host.
  Since then it has been renamed, its GPU checks made driver-aware, and its background
  replaced. None of that has run on hardware yet.
- Single display assumed for layout. With several displays the sprites are placed using
  the first one's geometry; check the others in `--preview`.
- SDR only. Plymouth draws 8-bit sRGB and sends no HDR metadata.
- `--preview` must run from a text console. While a graphical session holds the display,
  plymouthd cannot draw.

## Layout

```
plymouth/
├── install.sh                  install and select the theme, set GRUB keys, rebuild the initrds
├── uninstall.sh                restore the state recorded before the first install
├── verify.sh                   read-only checks; --preview renders without rebooting
├── prepare-boot-graphics.sh    is the KMS driver in every initrd? --apply / --revert
├── lib/common.sh               shared helpers, and the four system paths in one place
├── theme/
│   ├── quantum.script          the splash: background, spinner, fades
│   ├── quantum.plymouth.in     theme descriptor template
│   ├── background-wide.png     3440x1440, generated
│   ├── background-16x9.png     1920x1080, generated
│   └── wheel.png               the spinner, generated
└── build/
    ├── generate_backgrounds.py the default backgrounds
    ├── generate_wheel.py       the spinner
    └── prepare_backgrounds.py  your own art -> the two PNGs the theme expects
```
